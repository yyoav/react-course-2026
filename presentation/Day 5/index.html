What is Next.js?

A React framework with built-in features for production

🎯 Core Philosophy

React gives you the tools → Next.js gives you the structure

React Alone:

  • UI library only
  • You configure routing
  • You handle (Search Engine Optimization)
  • You setup build tools
  • Client-side only

Next.js Adds:

  • Full framework
  • Built-in routing
  • SEO-friendly by default
  • Zero config needed
  • Server + Client rendering

Why Use Next.js?

  • ⚡ Performance: Server-side rendering, automatic code splitting, and image optimization for lightning-fast apps
  • 🔍 SEO: Pre-rendered pages, metadata API, and sitemap generation make your site search-engine friendly
  • 🛣️ Routing: File-based routing with built-in layouts, loading states, and error handling

Why Use Next.js? (continued)

  • 🔧 Full-Stack: API routes, server actions, and seamless database integration
  • 📦 TypeScript: First-class TypeScript support with automatic type generation
  • 🚀 Deployment: One-click deploy to Vercel, or deploy anywhere you want

💡 A complete framework that handles routing, rendering, data fetching, and deployment

📁 Pages Router (Legacy)

The traditional Next.js routing system

Directory Structure 

my-app/
├── pages/
│   ├── index.tsx        ← / route
│   ├── about.tsx        ← /about
│   ├── blog/
│   │   ├── index.tsx    ← /blog
│   │   └── [slug].tsx   ← /blog/:slug
│   └── api/
│       └── hello.ts     ← API route
├── public/
├── styles/
└── package.json

How it works

  • Files in pages/ → routes
  • Each file exports a React component
  • Client-side rendering by default
  • Data fetching with getServerSideProps
  • Static generation with getStaticProps
  • _app.tsx for global layout

🆕 App Router (Modern)

The new recommended routing system since Next.js 13+

Directory Structure 

my-app/
├── app/
│   ├── layout.tsx       ← Root layout
│   ├── page.tsx         ← / route
│   ├── about/
│   │   └── page.tsx     ← /about
│   ├── blog/
│   │   ├── page.tsx     ← /blog
│   │   └── [slug]/
│   │       └── page.tsx ← /blog/:slug
│   └── api/
│       └── route.ts     ← API route
├── public/
└── package.json

How it works

  • Folders = routes, page.tsx = accessible
  • Server components by default
  • layout.tsx for nested layouts
  • loading.tsx for loading states
  • error.tsx for error handling
  • Async data fetching directly in components

Next.js has two routing systems

📁 Pages Router

(Legacy - Still supported)

  • pages/ directory
  • Client components by default
  • getServerSideProps
  • getStaticProps

🆕 App Router

(Recommended since Next.js 13+)

  • app/ directory
  • Server components by default
  • Layouts & templates
  • Streaming & suspense
  • Better performance

💡 New projects should use App Router

What Are Dynamic Routes?

Pages that handle variable URL segments with the same component

Static Routes (one page per path)
/product/shoes     → page.tsx
/product/laptop    → page.tsx
/product/headset   → page.tsx
❌ Can't create a file for every product!
Dynamic Route (one page, any value)
/product/[id]      → page.tsx

✅ /product/shoes
✅ /product/laptop
✅ /product/42
All handled by ONE component!

📂 Folder Convention

app/
└── product/
    └── [id]/          ← square brackets = dynamic segment
        └── page.tsx   ← receives { params: { id } }

How Params Travel: Server → Client

Understanding the data flow of URL parameters

🌐
1. Browser Request

User visits /product/42

⬇️
⚙️
2. Next.js Server parses the URL

Matches [id] segment → extracts params = { id: "42" }

⬇️
🖥️
3. Server Component renders with params

Can fetch data, query DB — params always strings

⬇️
📱
4. HTML sent to client (hydrated if needed)

Client Components can read params via useParams() hook

💡 Key point: params are always string — parse to number if needed: Number(params.id)

Dynamic Routes

Handle routes with parameters

Dynamic ID: app/product/[id]/page.tsx
interface Params{
  params: { id: string };
}
export default function Product({ params }: Params) {
  return (
    <div>
      <h1>Viewing Product: {params.id}</h1>
    </div>
  );
}

// URL: /product/123 → id = "123"
Multiple params
// app/shop/[category]/[id]/page.tsx
 interface Params{
  params: { category: string; id: string };
}
export default function ShopItem({ params }: Params) {
  return (
    <div>
      <p>Category: {params.category}</p>
      <p>Product ID: {params.id}</p>
    </div>
  );
}

// URL: /shop/phones/123
// category = "phones", id = "123"

Navigation with Link

Don't use <a> tags!
import Link from 'next/link';

export default function Navigation() {
  return (
    <nav>
      <Link href="/">Home</Link>
      <Link href="/about">About</Link>
      <Link href="/blog">Blog</Link>
    </nav>
  );
}

Why Link over <a>?

  • ✅ Client-side navigation (no page reload)
  • ✅ Automatic prefetching
  • ✅ Faster transitions
  • ✅ Preserves scroll position

What is a Layout?

A consistent UI wrapper that persists across multiple pages

💡 Layouts do not re-render when navigating. Only the Page Content mounts/unmounts.

Layouts - Shared UI

Wrap pages with shared components (nav, footer) 

// app/layout.tsx - Root layout for ALL pages
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <header>
          <nav>{/* Navigation */}</nav>
        </header>
        <main>{children}</main>
        <footer>© 2026 My App</footer>
      </body>
    </html>
  );
}

💡 Layout wraps all pages automatically - no need to import!

Visualizing CSR vs SSR

How the browser gets your UI

Client vs Server Rendering

Where does your component become <html>?

Client-Side Rendering (CSR)

  • Browser downloads a basic HTML shell (e.g., <div id="root"></div>) + JS.
  • React runs in browser, creating and mounting the UI dynamically.
  • Slower initial load, big JS bundle.
  • Used in traditional React (Vite).

Server-Side Rendering (SSR)

  • Server generates HTML.
  • Browser gets full HTML immediately.
  • React "hydrates" it to make it interactive.
  • Faster load, better SEO.

Server Components vs SSR

They are NOT the same thing!

Server-Side Rendering (SSR)

A technique where a Client Component is pre-rendered into HTML on the server. The JS is still sent to the browser, and the component "hydrates" to become interactive.

React Server Components (RSC)

A new type of component that executes ONLY on the server. Its code (JS) is never sent to the browser. It cannot use hooks or state, but it can safely access databases directly.

💡 RSC reduces bundle size. SSR improves initial load time. Next.js uses both!

Mental Shift Model

Thinking in boundaries

The Network Boundary

Server (Back-end)
  • Keep secrets safe (API keys)
  • Direct DB Queries
  • No JS sent to browser
  • Default in Next.js
Client (Front-end)
  • Interactive (onClick)
  • State (useState)
  • Browser APIs (window, localStorage)
  • Requires 'use client'

Server Components

The default in Next.js App Router

🖥️ Server Components

(default)

  • Render on server
  • Can access backend directly
  • No JavaScript to browser
  • Better performance
  • SEO-friendly

💻 Client Components

('use client')

  • Render in browser
  • Can use hooks (useState)
  • Can use event handlers
  • Interactive
  • Adds JavaScript bundle

💡 Use Server Components by default, Client only when needed!

When to Use Client Components

'use client';

import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </div>
  );
}

Use Client when you need:

  • useState, useEffect, or other hooks
  • Event handlers (onClick, onChange)
  • Browser APIs (localStorage, window)
  • Third-party libraries that use hooks

Data Fetching in Server Components

Super simple - just async/await!

// app/posts/page.tsx - Server Component
async function getPosts() {
  const res = await fetch('https://api.example.com/posts');
  return res.json();
}

export default async function PostsPage() {
  const posts = await getPosts();

  return (
    <div>
      <h1>Blog Posts</h1>
      {posts.map((post) => (
        <article key={post.id}>
          <h2>{post.title}</h2>
          <p>{post.excerpt}</p>
        </article>
      ))}
    </div>
  );
}

✨ No useEffect, no loading state management - it's automatic!

Data Fetching & Streaming

Show UI immediately while data continues to load

React Suspense

Instead of waiting for all data to load before showing the page, you can stream parts of the UI as they become ready. 

import { Suspense } from 'react';
import { PostFeed, WeatherWidget } from './components';

export default function Home() {
  return (
    <main>
      <h1>Dashboard</h1>

      {/* Renders immediately, shows fallback while loading */}
      <Suspense fallback={<p>Loading generic feed...</p>}>
        <PostFeed />
      </Suspense>

      <Suspense fallback={<p>Loading weather...</p>}>
        <WeatherWidget />
      </Suspense>
    </main>
  );
}

Static Rendering

Default behavior in Next.js

Static Rendering (SSG)

  • Pre-rendered at build time.
  • Incredibly fast (served from CDN).
  • Best for blog posts, documentation, marketing pages.

Dynamic Rendering

  • Rendered on-demand for each request.
  • Triggered automatically if you use cookies(), headers(), or URL searchParams.
  • Best for user dashboards, real-time data.

Rendering Strategies Overview

Next.js supports multiple rendering strategies

Strategy When Rendered Performance Use Case
SSG
Static Site Generation 		Build time ⚡⚡⚡ Fastest Blog, docs, landing pages
SSR
Server-Side Rendering 		Each request ⚡⚡ Fast User dashboards, personalized content
ISR
Incremental Static Regeneration 		Build + background updates ⚡⚡⚡ Fastest + Fresh E-commerce products, news sites
CSR
Client-Side Rendering 		In browser ⚡ Slowest initial load Interactive apps, private data

💡 You can mix strategies in the same app - choose the best for each page!

Which Strategy Should I Use?

Decision guide for data fetching

✅ Use SSG when:

  • Content doesn't change often
  • Same for all users
  • Can be pre-rendered
  • Examples: Blog posts, documentation, about pages, landing pages 
// Default in Next.js - just fetch!
export default async function Blog() {
  const posts = await getPosts();
  return <PostList posts={posts} />
}

✅ Use SSR when:

  • Data changes frequently
  • Personalized per user
  • Need request data (cookies, headers)
  • Examples: User dashboards, shopping carts, social feeds 
// Use cookies(), headers(), or searchParams
export default async function Dashboard() {
  const session = cookies().get('session');
  const data = await getUserData(session);
  return <Dashboard data={data} />
}

✅ Use ISR when:

  • Want static speed + fresh data
  • Content updates occasionally
  • Lots of pages (1000s)
  • Examples: Product pages, news articles, stock prices 
// Revalidate every 60 seconds
export const revalidate = 60;

export default async function Product() {
  const product = await getProduct();
  return <ProductPage product={product} />
}

✅ Use CSR when:

  • Private/sensitive data
  • Highly interactive UI
  • No SEO needed
  • Examples: Admin panels, real-time charts, private notes 
// Client component with useEffect
'use client';
export default function RealTimeChart() {
  const [data, setData] = useState([]);
  useEffect(() => {
    fetchData().then(setData);
  }, []);
  return <Chart data={data} />
}

Quick Decision Tree

Choose your rendering strategy

🤔 Does the data change?
❌ No → Use SSG (static generation)
✅ Yes → How often?
⏰ Every few minutes/hours → Use ISR (with revalidate)
👤 Per user/request → Is it public?
🌍 Yes, public → Use SSR (server-side)
🔒 No, private → Use CSR (client-side)

Pro tip: Start with SSG (default), opt-in to dynamic rendering only when needed!

Server Actions

Run secure server code directly from components

No absolutely need to write API routes (/api/*) just to handle a form submission. 

export default function Form() {
  // This function runs on the SERVER!
  async function createPost(formData: FormData) {
    'use server'; // The magic directive ✨

    const title = formData.get('title');
    await db.post.create({ title }); // Direct DB mutation!
  }

  return (
    <form action={createPost}>
      <input type="text" name="title" />
      <button type="submit">Submit</button>
    </form>
  );
}

Route Handlers (API Proxy)

Building APIs or proxying requests

Use route.ts to handle traditional API requests or proxy to an external backend (to hide API keys). 

// app/api/weather/route.ts
import { NextResponse } from 'next/server';

export async function GET(request: Request) {
  // Use securely stored environment variable
  const API_KEY = process.env.SECRET_WEATHER_API_KEY;

  const res = await fetch(`https://api.weather.com/v1/...&key=${API_KEY}`);
  const data = await res.json();

  return NextResponse.json({ data });
}

Next.js Best Practices

✅ DO

  • Use Server Components by default
  • Add metadata to all pages
  • Use next/image for images
  • Use next/link for navigation
  • Keep client components small
  • Use TypeScript

❌ DON'T

  • Use <a> tags for internal links
  • Fetch data in Client Components
  • Make everything 'use client'
  • Ignore loading states
  • Forget error handling
  • Skip metadata

  • Next.js is a React framework with built-in routing, SSR, and more
  • App Router uses file-based routing (folder = route)

  • Data fetching is simple with async/await
  • Built-in loading and error handling
